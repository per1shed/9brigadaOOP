# ЛР3. Правила добавления записей

Вариант: **Ledger**.

## Что дано

Предметные объекты, внешний API и вспомогательные типы уже подготовлены. В `app/domain/posting_rules.py` даны заготовки общего интерфейса и двух исполнителей. Их поведение и основной метод `LedgerService.record()` требуется завершить самостоятельно. Сигнатуры сохранены; новые слои и выбор архитектуры не нужны.

## Задание

### Шаг 1. Реализуйте общий интерфейс и два поведения

Реализуйте абстрактный класс `PostingRule` и два наследника.

`AllowedEntryTypeRule(types)` возвращает `ENTRY_TYPE_DENIED`, если направление не входит в набор. Пустой набор запрещает всё.

`MaximumEntryAmountRule(maximum)` разрешает `amount <= maximum`, иначе возвращает `ENTRY_AMOUNT_LIMIT`. Валюта настройки должна совпадать с суммой, иначе `CURRENCY_MISMATCH`. Нулевой максимум запрещает положительные записи. Сервис должен вызывать общий `check()` до сохранения.

### Шаг 2. Соберите путь вызова в `LedgerService.record()`

До добавления проверьте уникальность `entry_id` готовой `ensure_new_entry()`, затем правила по порядку. Отказ превращается в `DomainError(result.code)`. Единственная запись в хранилище выполняется после всех проверок. Не выбирайте алгоритм по конкретному классу исполнителя.

### Шаг 3. Проверьте повторное использование

После E1 попытка E2 сверх лимита отклоняется. Следующая корректная E2 допускается: ошибочная попытка не заняла ID.

## Примеры и границы

- В наборе `{DEBIT}` запись `DEBIT` проходит, `CREDIT` — нет.
- Максимум `1000` допускает `1000`, но не `1000.01`.
- Отказ или ошибка правила не добавляет запись; проверки суммы и уникальности сохраняются.

Последовательности и конфигурации дополнительно проверяются в `tests/test_progression.py`. Прочитайте ожидаемый результат каждого сценария до реализации.

Все проверки открыты: `tests/test_contract.py` и `tests/test_review_contract.py`.
Описание объектов — в [REFERENCE.md](REFERENCE.md), исходные результаты тестов — в [STARTER-STATE.md](STARTER-STATE.md).
